# 原版互传与 NFC：两条独立的 CryptoEng 路径

更新：2026-10-21。供体为一加 15 PLK110 ColorOS 17 C.76，目标为使用旧硬件底层的 8T。本轮独立分析用户提供的官方固件，没有引入其他移植项目的补丁。对端手机由用户手动操作；本记录不授予操作供体设备的权限。

## 10003 / 10045：缺失 HKDF 处理器

先定位原始状态和分发路径，再判断“缺什么信息”。本次 8T 管理器和直接 HIDL 路径都返回四字节小端 `10045`。公开 ARM32 TA 的扩展命令表不覆盖 `10003`，未匹配分支确实返回该值；请求尚未进入 HKDF 算法或标签解析。仅伪装机型、CPU、指纹或调用标签不能补出处理器。

原版 C.76 SDK 的请求为大端五整数头：`10003, 10000, 1, 600, JSON字节数`，随后 UTF-8 JSON。字段为 `only_key_label`、`key_label`、`info`、`salt`、`okm_len`、`hash`；salt/info 使用无换行 Base64，SHA-256 算法值为 2。接口含标签查询和实际派生两种请求，不能只实现一种。

供体 ARM64 TA 的这条 HKDF 分支使用固件内置的 OEM 协议材料，**在此分支没有读取个体 RPMB 记录**。这不是对整个 CryptoEng 或 NFC 密钥来源的结论。材料不收入公开 skill；重放时须从自己的已核验官方输入建立来源和内容校验。

验证计算的顺序：

1. 用 RFC 5869 公共向量检验独立实现。
2. 在隔离模拟器中执行供体实际 SHA/HMAC/HKDF 调用链，与独立实现比较多个 salt、info 和输出长度。本轮三组对照一致。
3. 处理 ELF 重定位和本机模拟所需 PAC 指令；这些调整仅发生在模拟器内存中，不是设备固件补丁。
4. TEE 初始化未运行时，不能沿用未初始化的分配回调。本轮最初 HMAC 偏差来自分配器 ABI：mbedTLS `calloc(count,size)` 必须正确相乘并清零，不能当作单参数分配器；纠正模拟环境后原生算法通过。
5. 实机比较实际管理器与直接 HIDL。普通 shell 的空应答或取不到服务属于权限/调用环境问题，不足以判断算法不支持；有效调用也只记录状态与长度，不输出派生密钥。

本轮兼容候选在真实硬件调用之后，仅针对 kona、原应答恰为四字节 `10045`、已验证的命令格式和原厂标签，执行真实 SHA-256 HKDF 并封装原协议应答；有界限制输入与输出长度。空应答、拒绝访问、未知标签、其它命令和原有成功结果保持原样。管理器路径成功而直接 HIDL 仍返回原错误，证明兼容层的实际落点。生产化还需复核调用方范围和新增资源的访问范围。

这是受限的缺失算法兼容，不能用于绕过 NFC 预置密钥检查，也不能将异常改为固定“成功”。

## 原版应用必须成组验证

本轮同时使用原版 OShare 和供体原版 IntentResolver，AccessoryFramework 与 OPSynergy 已和供体匹配；没有修改这些 APK 的版本号来适配协议。实验中仅撤下旧 OShare 专用 `Port8TQS17` 资源映射，其余 overlay 保持，以恢复新版原生磁贴映射。

旧 OShare 的防升级 versionCode 和旧 IntentResolver 兼容分支属于旧方案。迁移原版新版时，必须检查 `/data/app` 覆盖、高版本号降级判定、PMS 实际代码路径、分享目标和磁贴组件，而非只替换 APK 文件。不要全局放宽签名检查。

验收顺序为：实际包版本与原厂文件哈希 → 服务初始化 → 发现 → 连接 → 双向传输 → NFC。每一层分别记录；“所有人可见”、无报错、分享入口出现都不等于已传输成功。原版 APK 不再依赖 APK 内部补丁，但未来官方更新仍须重验框架协议，不能承诺永久兼容。

## 26 / 10023：NFC 预置数据与安全存储

NFC 原厂路径使用旧命令 26，携带包名和原始封装数据；命令在 8T TA 中存在，与缺少 10003 处理器不同。

本轮碰触日志的对应关系：

- NFC 已激活 ISO-DEP，并选择 `tapToShareReaderBasedOnTypeA: protocol=0`。
- AccessoryFramework 发现本地 `nfcPayload` 为空，请求重新初始化。
- OPSynergy 的预置数据接口反复返回 `10023`，`isSecretKeySupport: false`，初始化退出。
- NFC 随后因本地 payload 长度为 0 终止；不能把它当成触碰位置不对或单纯天线失效。

公开 TA 的调用链为 `hal_core_dec_preset_data` → `hal_redtea_rsa_dec_data` → 读取安全存储中 Redtea RSA 记录 → `hal_redtea_rsa_key_exist`。本轮封装数据 740 字节，声明长度为 32/256/256，满足 `196 + 三段长度`，不支持“改一下长度即可解决”的推断。记录内两项 RSA 分量长度不在 1..256 时返回 `10023`；哈希不匹配另有 `10017`。未读取实际安全记录，不能据此区分从未预置、记录无效等具体历史。

继续检查得到的反例：

- C.76 新 `hal_pki_preset_data_dec_handler` 仍调用这条预置解封链；仅换成新入口不能消除底层依赖。
- OTA 的独立 `oplus_sec` 安全模块和 ODM CryptoEng 是不同文件，需分别识别；本轮相关 RSA 常量一致，未发现能代替所需记录的分支。ARM64 供体模块不能直接刷到 ARM32 旧可信环境。
- 供体与 8T 公开固件中的内嵌 RSA 数据可还原出有效数学配对，但都不能解开这份 NFC 封装。验证采用严格 PKCS#1 v1.5、OAEP SHA-1/SHA-256；**配对有效不等于适用于当前封装**。
- 旧 OPSynergy 17.7.25、AccessoryFramework 17.6.6 与当前供体所含 NFC 封装相同；这些版本的回退没有提供另一份兼容材料。
- `cryptoeng_key_verify` 是模块校验回调序列，未发现其自动补齐 Redtea 记录。8T `rootkey_data_handler` 要求外部 0x608 字节 TLV（类型 7、内部长度 0x600），从输入写入三个用途的 RSA 记录；它不是无输入的初始化命令。没有执行此写入路径。

原版加解密类含失败返回原输入的分支，也不能推定无密钥即可完成手机协议；对端加密数据仍需解密，本地初始化又在生成 payload 前失败。协议 1 在所查 AccessoryFramework 中指向手表，不能作为手机兼容回退。没有部署关闭加密、强制支持、伪造密钥结果或写安全存储的候选。

下一次继续时，优先寻找并验证官方适用的预置/恢复路径或完整的原生手机兼容协议；当前没有可部署的 NFC 修复，不应重复要求用户碰触验证同一个失败候选。

## 框架 DEX 与 RAM 试验的两个坑

**隐藏 API 标记不能丢。** 本轮只修改 `CryptoEngManager.cryptoEngCommand` 一个现有方法，助手另置 DEX，原 87,888 个成员标记保留并核对 6,401 个类。直接反汇编含 hiddenapi 表的 DEX 曾触发工具越界；若使用绕过工具限制的检查副本，重建后必须从原始 DEX 恢复标记并重新检查，不能把移除表的检查副本当发布结果。

**撤 RAM 挂载不等于 APK 回退完整。** 停止框架后替换预装应用可能产生新版本 PMS 解析缓存；即使应用路径不变、正常重启使挂载消失，缓存仍可能与旧分区文件不一致。试验前备份确切两项 APK 缓存及属性。回退使用独立脚本：停框架 → 恢复对应原始缓存及属主、权限和标签 → 正常重启 → 回读原 APK、框架、磁贴映射和实际包版本，确认临时 root 消失与 SELinux 状态。缓存目录和文件名按当前设备定位，不照抄本轮路径，也不清空全部应用数据。

日志按当前 UID/PID 限时采集；服务重启可能换 PID。使用原始日志核对捕获窗口、实际字节数和标签，空的过滤结果不能否定用户已确认的实际传输。公开资料只保留审阅过的机制、结果和必要哈希，不上传原始日志、账号标识、密钥、签名凭据或固件。
