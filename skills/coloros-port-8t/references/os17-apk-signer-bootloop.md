# 应用优化进度回退：关键 APK 签名块遗漏

## 先区分编译进度与系统启动循环

20261028 整包现场表现为“正在优化应用”反复从1%到5%，随后重启。连续日志显示同一次内核启动里 system_server 多次退出，并非同一个普通应用反复编译失败。Data 仍有充足空间；不能据进度条先清缓存、清数据或改 dex2oat 参数。

实际失败链为：PMS 拒绝扫描 SettingsProvider，报告 `No APK Signature Scheme v2 signature`；随后系统中不存在 `settings` authority，EponaProvider 注册设置观察者抛出异常，system_server 退出。OplusExSystemService 也因同类签名块缺失被拒载。实机 APK 与发布镜像哈希一致，排除这次刷写传输损坏。

## 构建根因与修复范围

分身 GMS 修复的 APK 构建只用 zipfile 重写条目、再 zipalign。APK Signing Block 位于 ZIP 中央目录之前，不是普通 ZIP 条目，因此被丢弃。ZIP 条目内容相同、CRC 正确、DEX 往返通过和镜像逐文件一致，都不足以发现这个错误。

从精确匹配的原始 APK 保留原有签名块，并核对修复后每个 ZIP 条目的内容仍与功能候选一致。对齐完成后再放回签名块、修正中央目录偏移并校验结构。原始构建配方直接修正，避免每次合包追加事后修复步骤。

这仅恢复当前移植系统原有可信系统分区路径消费的签名元数据，**不是有效的 OEM 内容重签名**，不能用于普通 APK 安装或泛化为绕过签名校验的方法。没有取得 OEM 私钥，不扩大平台验证例外，不吞设置服务异常，不撤回 GMS 功能来掩盖失败。其他 ROM 必须先核对实际验证策略，不能照搬处理。

## 构建门禁

- 对最终镜像中的 SettingsProvider、OplusExSystemService、SystemUI 和 Settings 检查真实 v2/v3 签名块结构，不只看 META-INF 文件名。
- 若修改前 APK 有签名块，修改后必须保留匹配元数据；带缺陷的候选不能因哈希已冻结而绕过关键包检查。
- 区分“结构存在”“证书身份”“内容密码学验证”“PMS 实际接受”和“完整启动”，分别记录证据。
- 在没有旧包解析/签名缓存的场景验证关键组件注册。此前保留 Data 的冷启动成功没有暴露此缺陷，不能继续作为新整包干净启动通过的证据；清 Data 验证仍须获得授权。

新增预检准确拒绝旧发布输入中的两个缺陷 APK，并接受恢复后的两个 APK；Settings 和 SystemUI 的签名结构保持。全量内容/权限/标签回解审计继续执行，不用新增预检替代原有检查。

## 容量与验收

第一候选仅超原 system_ext 8192字节，原生 fastbootd 的 resize 返回失败。先回读 Super 元数据，确认与调整前完全一致，再停止尝试。不能截断镜像或因物理 Super 足够就忽略逻辑分区容量。

最终将 SettingsProvider 的 DEX 采用标准 ZIP 压缩，DEX、资源内容和功能均不变；重新构建后装入原逻辑分区，保留 legacy EROFS 与全部元数据。未通过的增长候选不进入最终清单。

2026-10-31 修复分区完整写后回读，在保留 Data、原 NoRoot boot、原 LP 布局与 Enforcing 的条件下，约169秒进入“你好”首次设置向导；启动完成后连续四次采样中 boot_id 和 system_server PID 保持，两个服务注册，原致命错误未再出现。未代用户推进向导。

这证明单分区修复在该现场有效，不等于新版完整包已再次双清安装、另一槽位或全部8T变种都验收通过。另一条非致命 AON overlay 签名拒载仍需单独归因，不能扩大为“所有 APK 签名问题已消除”。
